## 1. 已确认目标与本轮建议

已确认：工作空间属于 Timeline，保存共享记忆、世界演进、草稿、图片和脚本；剧情回到历史状态时，工作空间必须一起恢复。共享作者 Lore 不随剧情回退，新生成使用当前作者资源。默认共享 `MEMORY.md` 保存跨 Session 的暗线、大纲和共同安排；2026-10-20 已改为各 Session 另有自身连续性交接摘要，独立管理执行记录、摘要版本及历史压缩边界，不与共享文件维护相同正文镜像。

以下是待确认的共同合同建议，不将提出方案当作授权实施：各交互负责选择目标，共同恢复入口负责校验和采用运行数据版本。复用现有 Store 和 Data Engine，不建立通用事件溯源系统、不倒序撤销整段 Changeset、不要求各领域共用一种版本存储。

## 3. 恢复范围

| 数据 | 建议合同 |
| --- | --- |
| 正文路径 | 采用目标 Narrative Head；保留其他历史节点 |
| Timeline State | 采用目标 State Revision；不恢复 Global State |
| Workspace | 采用完整工作树版本，包括目录、文件身份与内容引用、移动/删除、MEMORY、世界演进、脚本、图片引用及文件的被动注入配置 |
| Session 摘要 / Run / Tool 事实 | 不删除、不反写历史；下一次输入只采用与目标剧情相容的摘要版本及完整工作段，不能只按全 Session 最新摘要截断 |
| 剧情摘要 | 必须选到与目标剧情相容的已采用视图；数据和算法仍由记忆来源拥有，见第 8 节 |
| 作者 Lore、Preset、原包脚本、权限授予 | 保持各自生命周期；恢复旧文件或配置不能恢复已撤销权限 |
| 外部调用及执行内存 | 不撤销网络副作用，不重放工具，不恢复 JS 闭包、定时器或进程内存 |

工作空间按 Timeline 归属、按 Branch/候选选择可写版本。分支共享不可变历史和 Blob，修改后各自演进；不能只建立一棵全 Timeline 可变目录。

2026-10-18 用户进一步明确：Workspace 与 State 属于同一恢复粒度，可以在任意合法工作时点高频变化，不受楼层/Token 总结周期约束；MEMORY 只是其中一个文件。剧情原文缓冲只降低剧情摘要失效的频率，不保护 Workspace，也不决定其保存与恢复边界。撤回第 40 楼所对应的尝试时，采用生成前基线的完整工作树，第 40 楼后的 MEMORY、草稿、脚本等变化一起退出当前版本，不逐文件判断是否属于总结。

Blob 字节与目录引用分别处理：恢复前不再可见的文件及图片引用退出当前工作树，但字节可由其他历史或产物记录继续保留。迟到图片可以保存为归属原任务的产物，不能强行挂进新工作树；产物保留及访问沿所属能力接线，不在此额外建设“回收箱”。

## 4. 一个恢复点表达什么

一个恢复点记录同一时刻已提交的领域引用，概念上包含：

```text
所属 Timeline 与产生位置
  Narrative Head（允许空正文）
  State Revision
  Workspace Revision
```

这是一组一致引用，不是另一份内容副本。恢复请求应选择已有恢复依据，不能让调用者任意拼接正文 A、State B 和工作树 C。接口名、是否需要独立 ID/表、引用如何放入现有 Branch/Node/Swipe 记录，留给确认后的文件级设计。

当前 Branch 仍有实时的各领域 Head。普通单领域写入只创建该领域修订并推进对应 Head，同事务记录提交事实；不要求每次都复制整组内容或生成一次完整故事快照。恢复点中的引用必须在同一数据库一致视图下取得。

不以 `runId`、墙钟时间或 Changeset 顺序反推缺失的历史依据。相同节点可以先后有多个合法工作树状态，所以节点 ID 本身不是完整恢复点。

写入频率澄清（2026-10-18）：捕获恢复依据不要求 Agent 同时更新 MEMORY 或其他文件。工作记忆通常在 Session 需要整理/交接时保存，其他工作文件按实际任务写入；工作树没有变化的多个历史点可以引用同一 Workspace Revision。恢复返回当时实际已保存的材料，不自动生成该楼层的工作摘要，也不拿未来才写下的 MEMORY 补齐过去。

### 复用 Swipe 已有的正文与工作记录关联

当前 [Narrative 类型](../../../packages/application-data/src/narrative/types.ts) 已提供节点来源字段 `agentSessionId / agentMessageId / runId`，但它们可选，不足以独立构成完整恢复点。更直接的运行依据已在 Swipe 中保存：Group 记录 `inputNodeId`、`baselineStateRevisionId`、`agentSessionId`、`baseEntryCount`；Candidate 记录 `runIds`、`headNodeId` 与结果 `stateRevisionId`。

[Swipe Runtime](../../../packages/application-runtime/src/runtime/swipe-runtime.ts) 在生成前恢复正文/State 基线，并通过候选 Run 排除规则选择 Session 工作段，保留原始 Transcript。它是共同恢复可复用的原型，不需要重新按“一个楼号对应一条 Session 消息”建模。待补内容是在同一基线/候选成果中关联 Workspace Revision，并把交接消费边界纳入目标选择；具体字段或公共恢复引用由实施设计决定，不在这里为每个操作复制独立方案。

尤其要补交接的来源归属：当前宿主追加的 work-summary 没有候选 `runId`，不能期待仅排除废弃候选 Run 就自动排除交接。应能将它关联到所依据的分支/候选及安全工作边界；它可以是独立宿主交接任务，不冒充原生成 Run。回退时工作树恢复旧 MEMORY，Session 同时不再采用基线之后失效的交接，再按合法边界加载工作记录。

关系不依赖消息数量一一对应：一次尝试可以有多次工具执行、无正文写入或多个正文节点，Workspace 也可能先于正文变化。因此记录的是完整尝试之前的基线及结果归属；任意中间节点回退还要遵守第 5 节的实际捕获点，不能把最新单回复 Swipe 的能力直接宣称为任意历史恢复已实现。

## 5. 捕获时点建议

| 时点 | 保存什么、用途是什么 |
| --- | --- |
| Timeline 初始化完成 | 初始正文、State、含默认 MEMORY 的工作树；初始化失败不发布半个工作空间 |
| 第一次写作尝试开始前 | 输入已确定、任何本次生成副作用发生前的共同基线；没有成功正文也能从头重试 |
| 正文节点提交 | 同事务留下该节点提交时的 State/Workspace 引用，作为节点提交点；不冒充 Run 最终成果 |
| 候选成功完成 | 当前正文、最终 State/Workspace，作为候选成果依据；覆盖“先写正文、后改变量或记忆” |
| 当前候选完成后继续编辑 | 正文/State/Workspace 合法修改计入当前成果；原执行基线不改变。切离候选或接受下一条故事输入前固定其最新成果引用 |
| 无候选的当前故事末端被编辑 | 更新当前 Branch 运行状态；离开该末端前保存对应结果，不能让无 Swipe 的手工操作失去历史依据 |

本表描述引用捕获与已有成果归属，不规定每一行都调用模型写文件。剧情摘要的楼层触发、提前准备和后续采用继续归[剧情记忆计划](../../archive/plans/narrative-memory-and-refresh-policy-plan.md)，不由恢复入口判断或触发。

推荐的历史查找语义：从某条分支的历史末端分叉，采用该末端离开前最后保存的成果；尚未离开的当前末端采用当前 Branch 状态。一次运行内较早的中间节点只承诺其实际提交点，不用最终成果倒填所有前序节点。开始后续尝试前固定旧结果，新尝试在写正文前产生的 State/文件变化不能反写成旧剧情的成果。

历史成果映射要区分分支/候选，不能原地修改跨 Branch 共享的 Narrative Node 来给某条分支补新版本。编辑历史正文造成的节点替换需要保留对应关系，但不据此重算后续事件；相关摘要是否仍有效由记忆合同处理。

以上“历史末端采用离开前最后保存成果”是本轮产品建议，尚未批准。它比现有历史分叉只取 `node.stateRevisionId` 的行为更完整，也意味着需要显式补齐历史依据。

## 6. 各交互只决定目标与候选资格

| 操作 | 目标与行为 |
| --- | --- |
| Swipe 切已有候选 | 保存离开候选的最新成果，采用目标候选整组引用；不运行模型和工具 |
| 新增 Swipe 候选 | 保留旧候选，从共同基线开始新尝试；新写入即时可见 |
| 重试/重新生成 | 按既有规则使本轮旧候选不可选，采用原输入基线再执行；最终失败留在基线，不恢复旧候选 |
| 修改输入生成候选 | 原输入之前的依据与新输入后的执行基线都必须明确；不能用旧输入节点混入生成后的工作树 |
| 正常失败/放弃新尝试 | 沿既有 Swipe 规则采用输入基线并保留失败事实；修改既有候选失败则采用修改前成果，见现有 finish 流程 |
| 检查点继续 | 不采用故事基线；只有来源与检查点仍有效才接续，不重放已完成或结果未知的工具 |
| 从历史位置创建 Branch | 以目标恢复点初始化新的 Branch；原 Branch 和历史不变，后续写入分离 |
| 切换已有 Branch | 选择该 Branch 自己的当前运行状态；不把另一个 Branch 的工作树复制过来 |
| 删除尾部并回退 | 若提供此产品操作，采用保留端的恢复点；本轮未查到独立的通用删尾入口，不声称已实现 |
| 删除单个文件/撤销文件编辑 | Workspace 自己生成新版本，属于普通编辑，不自动回退正文与 State |
| 删除 Timeline | 同事务撤销目标可见性、处理所属数据并使写入来源失效；属于生命周期清理，不是恢复点采用 |

创建分支、候选选择及权限仍由各入口拥有。共同层只负责同一组领域版本的验证、捕获与采用，不用一个任意 action dispatcher 代替所有业务入口。

## 7. 原子采用与并发

建议共同流程：

1. 解析明确的目标与来源。正在修改同一候选的主写作必须先按现有规则完成或停止；suspended 先继续或明确放弃，不直接丢弃检查点。取消信号本身不是停止成功。
2. 进入共享 Data Engine 事务，重检当前 Head、候选/分支版本及恢复目标；固定离开成果所需引用，检查目标各修订存在且归属正确。
3. 在同一事务内采用正文、State、Workspace，更新相应候选/Branch 关系及执行来源的有效代际。任一核心验证或写入失败，整次数据库采用失败。
4. 提交后通知消费者刷新同一状态组合。UI/Prompt 的多次读取需要使用一致的采用标识或复核，不能仅因数据库原子提交就宣称跨请求读取也是快照。
5. 清理过期执行上下文，准备目标所需的记忆视图和脚本实例。数据提交成功与运行准备成功分别报告，准备失败不伪称数据回滚，也不让错误上下文开始新的写作。

执行来源保护与内容版本检查不同：前者阻止旧剧情任务写进新剧情，后者防止同一剧情中的并发覆盖。必须同时保留。代际只在使旧执行来源失效的转换时更新，不应把每次普通文件保存都变成全体任务失效。可复用/推广现有 source generation 与事务守卫，不在本文预定第二套 token 系统。

绑定贯穿 Prompt、主动读取、工具、脚本和扩展写入；不能在完成时查询 UI 当前 Timeline。普通写入和共同恢复通过同一 Engine 排队、在事务内判定先后：切换前成功的写入纳入离开成果，切换后的过期写入被拒绝。单纯浏览另一个 Branch 不等于授权任务改绑；原目标是否仍允许后台执行由已确定的生命周期控制，不把所有浏览切换等同于取消全部任务。

独立后台任务不作为全局锁。受管宿主的权限和写入凭据必须能失效；对无法终止或绕过宿主的数据写入环境，不能声称支持安全恢复。停止/启动进程是事务外行为，不把它们伪装成 SQLite 可回滚操作。

## 8. MEMORY、剧情记忆与执行实例

### 共享 MEMORY 与 Session

MEMORY 的内容和注入配置随工作树恢复；Session 自有摘要按完整来源选择相容版本，原始工作事实保留。重试/Swipe 复用现有候选工作段过滤，不能继续注入废弃未来的 work-summary。保存旧摘要版本不等于继续采用其文本；共享文件恢复也不自动替代 Session 摘要选择。

2026-10-20 缓冲规则要求区分状态依据与历史压缩位置：看完截至 40 的工作、仅压缩到 32 的交接仍可能包含第 40 楼状态，回到 39 时不能直接采用；只依据剧情 1～32 的摘要则可能继续有效。异步结果保存位置不代表其压缩截止位置。Session 当前只有一个有效摘要，不意味着物理覆盖后无法恢复旧版本；若开放普通摘要编辑，编辑不自行推进压缩位置，也不能把新事实标成旧来源。完整规则见[剧情记忆计划第 14 节](../../archive/plans/narrative-memory-and-refresh-policy-plan.md)。

对任意历史分支或回退，先前建议复用已有“干净 Session 从目标剧情与共享记忆开始”的方向；后续讨论指出，这会遗漏仅存在于原 Session 摘要或工作段中的进度，不能等同于完整恢复工作记忆。因此另比较“关联目标 Session 的安全执行边界，恢复有效摘要与其后保留工作段”，详见[剧情记忆计划第 11 节](../../archive/plans/narrative-memory-and-refresh-policy-plan.md)。两者仍是恢复产品候选，不在本轮改写既有 Swipe 行为，也不删除 Session 原始事实。主写作选择/创建继续与[主写作计划](./agent-trigger-and-standing-resource-bindings-plan.md)收束；没有合法工作段或明确的重建方案时，不能恢复文件后仍沿用未来对话。

### 剧情摘要

最新回复 Swipe 沿用近期缓冲合同，不另建 Swipe 摘要回滚。任意历史回退/分支则必须由记忆来源提供与目标相容的已采用结果；不能因为覆盖节点仍存在就默认当前摘要可用，也不能偷偷采用最新 100 节点回退策略。

本轮不决定将插件私有存储全部纳入平台事务。后续需收束记忆来源对历史视图的选择/准备接口，及必要的持久版本依据。缺少相容视图时可以完成核心数据恢复，但必须明确上下文尚不可用于继续写作；不自动生成摘要、不冒充整个恢复流程已就绪。核心数据原子性和消费者准备是不同保证。

2026-10-18 后续分层讨论见[剧情记忆计划第 9、11 节](../../archive/plans/narrative-memory-and-refresh-policy-plan.md)：摘要单元与“已采用组合”分别保存，建议恢复依据关联发布/来源版本，而非按当前分支直接采用最新结果。生成于第 40 楼、实际只依赖未变化的 1～32 楼的摘要，回到 39 楼仍可复用；该单元不因创建时间较晚而删除，采用视图的 Raw 上界则不能越过目标，且须与有效 Session 工作段避免重复消费。回到某份高层摘要覆盖范围中间时，只能选择符合目标前缀的下层/旧视图或合法原文，不能将高层摘要任意截断。具体发布引用及主写作工作历史选择怎样与三项核心数据接合仍待设计，不以此段宣称原子恢复已包含扩展私有数据或完整 Session 投影。

### 脚本

工作区代码属于工作树，脚本内部需要随剧情恢复的持久数据应写到受管 State/Workspace。启用配置与运行版本的历史关联仍需[脚本计划](./loom-script-distribution-and-runtime-plan.md)定稿；只保存源码不代表已经覆盖持续运行程序。

硬性要求：恢复后旧实例不能再向新状态提交。建议对受影响的工作区实例撤销旧上下文并按目标版本重建；不恢复旧内存，不重放已发生事件。作者/全局实例不一律重启，但其旧 Timeline 调用凭据仍必须失效。切离 Timeline 是否停止工作区实例、哪些配置随恢复，仍是未确认建议。

## 9. 存档、保留与存量数据

工作树历史、恢复点引用及所引用 Blob 必须进入 Timeline 存档携带范围；不能只导出当前文件而留下不可恢复的候选。删除 Timeline 与引用保留/物理 GC 分开处理。

现有 archive participant 在核心导入提交后执行，允许独立失败；不能直接拿它承诺核心工作树与正文/State 一起恢复。实现时需让核心工作树元数据进入同一导入事务，并明确 Blob 准备及引用完整性校验。失败后暂留无引用字节可以沿 Blob 现有模型处理，不删除可能共享的字节。

旧记录缺少工作树历史时，不能拿当前文件充当过去版本。迁移时区分“此前未启用该功能，确实无工作文件”与“应有版本但记录缺失”；可承诺哪些历史范围必须在迁移设计中明确，不在本轮运行用户数据迁移。

## 10. 待决定与最小验收

需要用户收束的产品问题：

1. 是否接受第 5 节的历史末端语义：离开前最后保存的成果，而不是只恢复到正文刚提交时。
2. 任意历史回退时，干净主写作 Session、记忆来源准备与脚本重建的使用体验；已有 Swipe/继续规则不重开。

技术实现继续核查但不要求用户选表结构：历史引用和 Node 替换关联、共同事务入口、代际覆盖面、存档字节闭包、旧数据迁移，以及记忆来源的能力接缝。具体脚本后台生命周期仍在所属计划收束。

最小后续验收场景：

- 先写正文、后改变量/MEMORY/脚本并移动图片；切 A/B、重试和从历史分支都恢复对应整组内容及目录/注入配置。
- 当前候选的人工编辑留在该候选；新尝试基线不被改写；两分支继续修改互不影响。
- 无正文失败仍能恢复原基线；suspended 继续不先回退，结果未知工具不重放。
- 任一核心采用失败不产生混合 Head；切换中的读取不把旧正文与新工作树组合成同一次 Prompt。
- 旧后台任务不能读取/写入新候选，独立资产保留但不误挂；脚本启动失败不伪称持久恢复失败。
- 文件恢复后不注入未来 Session 摘要或剧情记忆；来源无有效历史视图时准确阻止继续构建。
- 重启及导出导入后仍能解析被保留恢复点与 Blob；删除 Timeline 后旧写入被拒绝，其他 Timeline 和共享作者资源不变。

本轮交付仅为这份讨论草案及相关计划索引同步。核对文档 Diff 与链接，不执行业务测试，不宣称上述场景已经通过。

## 11. 模块精简约束（2026-10-19，2026-10-20 修订）

本节记录用户要求纳入 Plan 的模块精简建议，供后续实施收束；不启动代码修改、迁移或改变此前尚待决定的产品行为。关系图中的函数、记录类型与处理步骤不自动成为独立模块。

### 已确认的工作记忆归属

共享工作记忆属于 Timeline Workspace，按当前 Branch/候选采用工作树版本，默认 `/workspace/MEMORY.md`。Session 自有摘要负责自身工作连续性，固定注入、只有一个当前有效条目且受容量上限约束；独立 Session 无需 Workspace。绑定 Timeline 的交接由当前 Agent 保存自身摘要并维护共享 MEMORY，不另设总结 Agent。

当前 [Session 交接入口](../../../packages/application-runtime/src/runtime/agents-runtime.ts) 已把交接文本保存为 Session 的 `work-summary`。这是可复用的自有摘要基础，但来源/压缩边界、版本选择、可选异步和编辑能力仍未完成，不能把本次归属调整记为已交付；具体 KV 或专用记录形态未冻结。

### 建议落实的五处精简

1. **Workspace 恢复并入现有共同恢复操作。** 复用 Swipe 的基线/候选关系和 `restoreBranch` 所在事务路径，同一次采用中校验并选择正文、State、Workspace 引用。各交互继续负责选择目标，不新增监听 Narrative 回滚后再执行的 Workspace 回滚管理器，也不倒序撤销整段 Changeset。Blob 字节与消费者准备仍遵守原有事务边界。

2. **各类内容各有一份权威正文。** Session 自有摘要与 Timeline 共享 MEMORY 分别负责接续状态和共同安排，不同步维护同一摘要的两份镜像。先限定目标下合法的工作来源，再选相容摘要及保留工作段；共享 MEMORY 从当前采用工作树消费，不被旧 Session 摘要引用永久锁定。保留原始 Transcript 和旧摘要版本；单一当前条目不等于原地破坏历史。摘要编辑不自动推进历史压缩边界，字段/API 留给实施设计。

3. **历史摘要选择纳入现有剧情来源解析。** 沿 [NarrativeContextRegistry](../../../packages/application-runtime/src/narrative/context-provider.ts) 及 Provider 合同补充目标恢复依据。来源根据自身摘要结构选择相容组合，宿主/Registry 校验归属和范围，不另建持有第二套当前摘要指针的记忆回滚器。共用 Narrative 采样器继续服务被动投影和主动读取，不合并其读取职责与来源私有算法；具体接口参数尚未冻结。

4. **摘要记录直接使用既有扩展存储。** 首版官方实现拟以摘要单元和发布记录作为 Extension Record 的业务类型，通过已有 API 与 Document Store 保存，不另开数据库，也不为转接相同 API 预建多层 Summary Store / Repository / Adapter。若出现明确的查询、事务或规模需求，再补对应能力。[现有数据合同](../../architecture/application/extension/data-and-portable-payload.md) 的版本/CAS 不自动构成分支恢复或历史视图。

5. **Run 结束检测共用一处入口。** 在可整理边界分别判断剧情整理和工作交接条件，不为两项任务各建常驻调度器。剧情可以提前异步准备；正常游玩的 Session 整理待下一条主聊天输入成功写入正文后才启动，同步或可选异步按已选策略采用。两种总结仍分别提交和报告失败；共享检测不意味着整体原子提交，Session 摘要与 MEMORY 两项写入的部分失败仍待所属计划收束。

### 保留的职责边界与后续验收

State 的结构化变量与 Workspace 文件树继续分开；Narrative 故事事实与 Session 执行事实继续分开；剧情摘要按来源范围组织，共享记忆随工作树更新，Session 摘要按来源和压缩边界选择；核心数据库采用与消费者准备分别报告结果。共享恢复入口不要求各类数据合成一种 Store 或快照格式。

后续实施应能观察到以下结果，不把本次文档检查当成行为验证：

- 依据第 40 楼状态交接后回到第 39 楼，正文、State、工作树、Session 摘要和有效工作段共同适用于目标；不能因历史只压缩到 32 就继续注入截至 40 的工作状态。来源未变的 1～32 楼剧情摘要仍可复用。
- 共享工作记忆从当前工作树消费，Session 摘要从相容版本注入一次，二者不维护同正文镜像；共享文件后续合法修改不被旧交接引用遮蔽。
- 保存失败不提前切段；剧情来源发布失败与 Session 交接的实际提交结果分别报告。恢复入口、来源解析和检测流程不依赖新增的平行管理器/调度器互相同步。

优先级沿既定建议：Workspace 与共同恢复先落实第 1 项及必要交接归属；工作交接阶段落实第 2 项；剧情 Summary 与整体验收阶段落实第 3～5 项。本文不扩大为资源目录重构、所有 Session 迁移或新的通用存储平台。
